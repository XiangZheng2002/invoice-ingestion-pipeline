# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Email Invoice Recognition System - A Flask web application for Chinese invoice (发票) processing. Two input paths: (1) drag-and-drop upload of invoice files, (2) automatic IMAP fetch from QQ Mail with invoice-email detection. Extracted data is exported to CSV for expense reporting.

**Recognition strategy (important)**: Chinese electronic invoices (数电票 / 增值税电子普通发票) ship as PDF or OFD files that carry a real text layer — and often an embedded structured XML. These are parsed directly, offline and free, with higher accuracy than OCR. Baidu OCR is only a fallback for images and scanned documents, and is entirely optional.

## Development Commands

### Setup
```bash
# Create virtual environment
python3 -m venv venv

# Activate virtual environment
source venv/bin/activate  # macOS/Linux
venv\Scripts\activate     # Windows

# Install dependencies
pip install -r requirements.txt
```

### Running the Application
```bash
python run.py                     # opens a native desktop window (pywebview)
BILL_BROWSER=1 python run.py      # browser instead of a window
BILL_NO_WINDOW=1 python run.py    # server only, no UI — use this for automated checks
BILL_DEBUG=1 python run.py        # enable Flask debug (dev only; ignored when frozen)
```

The port is chosen at runtime (5000 first, then 5001/5002/8000/8080, then anything free) —
**do not hardcode 5000**; macOS AirPlay Receiver occupies it on many machines. The startup
banner and `logs/app.log` both print the actual URL.

### Packaging
```bash
./build_app.sh      # macOS/Linux
build_app.bat       # Windows
```
See `PACKAGING.md`. PyInstaller cannot cross-compile — `.github/workflows/build.yml`
builds both platforms in CI.

### Environment Configuration
- Copy `.env.example` to `.env` (if exists) or create `.env` with required variables
- Required environment variables:
  - `SECRET_KEY`: Flask secret key
  - `ENCRYPTION_KEY`: Auto-generated by CryptoUtil on first run, must be saved to `.env`
  - **Baidu OCR credentials are now configured via web interface** (see below)

### Baidu OCR Configuration (optional)
- **OCR is not required** for electronic invoices — PDF/OFD go through `PDFInvoiceParser`
- Needed only to recognize image attachments and scanned documents
- OCR credentials are configured through the web UI at `/config`
- Users enter their own Baidu OCR credentials (APP_ID, API_KEY, SECRET_KEY)
- Credentials are encrypted and stored in the `config` table
- `OCRService` reads from database first, falls back to `.env` if not found
- This allows multi-user deployment where each user uses their own OCR quota

### Running Tests
```bash
# PDF/OFD direct-parse regression test (generates its own fixtures, no network)
python test_pdf_parser.py
```

## Architecture

### Application Structure
- **Entry Point**: `run.py` - Creates and runs the Flask app
- **App Factory**: `app/__init__.py` - `create_app()` initializes Flask, CSRF protection, database, and registers blueprints
- **Configuration**: `app/config.py` - Config class with environment-based settings
- **Database**: SQLite with direct connection management (no ORM)

### Layer Organization

**Models Layer** (`app/models.py`):
- Direct SQLite3 connections via `get_db_connection(db_path)`
- Model classes: `Email`, `Invoice`, `Config`
- Each model has static methods: `create()`, `get_all()`, `get_by_id()`, `count()`
- Database initialization: `init_db(db_path)` creates 4 tables: emails, invoices, config, export_history

**Routes Layer** (`app/routes/`):
- Five blueprints: `main.bp`, `email_routes.bp`, `invoice.bp`, `config.bp`, `upload.bp`
- Registered in `app/__init__.py`
- Routes handle HTTP requests and delegate to services
- `upload.bp` (`/upload`): drag-and-drop page + `POST /upload/api` which saves each
  uploaded file, runs `InvoiceExtractor`, dedupes by invoice number, and stores the result

**Services Layer** (`app/services/`):
- `InvoiceExtractor`: **the single entry point for recognizing an invoice file**.
  Tries direct parsing first, falls back to OCR. Both the upload route and the email
  route go through it — do not call `OCRService` directly from routes.
- `PDFInvoiceParser`: offline extraction from PDF/OFD, no network, no credentials
  - Priority: embedded invoice XML → PDF text layer → OFD `TextCode` elements
  - Field extraction by regex over the text (发票号码/代码, 开票日期, 购销方, 金额/税额/价税合计, 校验码)
  - Buyer vs. seller are disambiguated by **x-coordinate** (`_fields_by_column`), because
    数电票 puts the two blocks side by side and plain text order is unreliable
  - Returns `success=False` when no text layer or no valid number+amount, so OCR takes over
- `EmailService`: IMAP connection to QQ Mail, email fetching/parsing, attachment handling
  - Connects to `imap.qq.com:993` with SSL
  - Key methods: `connect()`, `fetch_emails()`, `parse_email()`, `download_attachment()`
  - Handles date filtering with client-side fallback for QQ Mail IMAP bugs
- `InvoiceDetector`: Rule-based invoice email detection
  - Multiple detection strategies: keywords in subject/body, known sender domains, attachment analysis
  - Methods: `is_invoice_email()`, `detect_invoice_type()`, `extract_invoice_files()`, `get_detection_confidence()`
- `OCRService`: Baidu OCR integration, used only as fallback for images/scans
  - Uses `AipOcr` client with VAT invoice API (`vatInvoice()`)
  - Parses structured invoice data from OCR results
  - Falls back gracefully if OCR not configured
- `csv_exporter.py`: CSV export functionality
- `file_handler.py`: File processing utilities
  - `pdf_to_images()` renders with **PyMuPDF**, not pdf2image — pdf2image needs the
    external poppler binary, which PyInstaller cannot bundle and which breaks on
    end-user machines. Do not reintroduce it.

**Utils Layer** (`app/utils/`):
- `crypto.py`: `CryptoUtil` class using Fernet (symmetric encryption) for QQ Mail password storage
  - Auto-generates encryption key on first run if not in `.env`
- `validators.py`: Input validation and sanitization

### Data Flow

1. **Email Fetching**:
   - User configures QQ Mail credentials via `/config` route
   - Credentials encrypted by `CryptoUtil` and stored in `config` table
   - `EmailService.connect()` → `fetch_emails(since_date, before_date)` → `parse_email()`
   - Email data saved to `emails` table via `Email.create()`

2. **Invoice Detection**:
   - `InvoiceDetector.is_invoice_email()` analyzes subject, sender, body, attachments
   - Detected invoices marked with `is_invoice=True` in database
   - Invoice types: PDF attachment, image attachment, email body, electronic invoice link

3. **Invoice Recognition**:
   - Invoice files extracted via `InvoiceDetector.extract_invoice_files()`
   - `InvoiceExtractor.extract(file_path)` decides how to read them:
     - PDF/OFD → `PDFInvoiceParser.parse()` (embedded XML → text layer)
     - image / scan / failed direct parse → `OCRService.recognize_invoice()`
   - Result carries `parse_source` (`xml` / `pdf` / `ofd` / `ocr`) and a confidence score
   - Deduplicated by `invoice_number` before insert
   - Invoice records created in `invoices` table with foreign key to `emails.email_id`
     (`email_id` is NULL for files uploaded directly)

3b. **Direct Upload** (no email, no OCR needed):
   - `POST /upload/api` with multipart `files`
   - Same `InvoiceExtractor` path; frontend uploads one file per request for per-file progress

4. **Export**:
   - Query invoices from database
   - Generate CSV with expense report fields
   - Track exports in `export_history` table

### Desktop Packaging Constraints

This ships as a double-clickable app to non-technical users. Four rules follow from that,
and breaking any of them produces a bug that only shows up on someone else's machine:

1. **Paths** — `app/paths.py` is the single source of truth. Read-only resources come from
   `sys._MEIPASS`; data (DB, key, attachments, logs) goes next to the executable. Relative
   paths in config (`LOG_FILE=logs/app.log`) resolve against `get_base_dir()`, **never** the
   CWD — launching from Finder gives a CWD of `/`.
2. **No `print()` assumptions** — with `console=False`, `sys.stdout`/`sys.stderr` are `None`
   on Windows and a bare `print()` raises `AttributeError`. `app/logging_setup.py` rebinds
   them to the logger and installs an `excepthook`. It must run before anything prints,
   which is why `create_app()` calls it.
3. **Debug is force-disabled when frozen** (`run.py`). The Werkzeug debugger is arbitrary
   code execution; it must never reach a distributed binary.
4. **Secrets are not bundled** — the spec excludes `.env` unless `BILL_BUNDLE_ENV=1`.
   Each machine generates its own `data/encryption.key` on first use.

### Security Considerations

- **CSRF Protection**: Enabled via `flask_wtf.csrf.CSRFProtect()`
- **Password Encryption**: QQ Mail passwords encrypted with Fernet before database storage
- **Encryption Key Management** (`app/utils/crypto.py`): resolved in order —
  `ENCRYPTION_KEY` env var → `data/encryption.key` → generated and written (mode 0600).
  The key is cached per process and **must** be persisted; the earlier implementation
  generated a throwaway key per `CryptoUtil()` instance, so encrypt and decrypt used
  different keys and stored passwords became unreadable. Losing the file means re-entering
  the mail auth code and OCR keys (invoice data itself is not encrypted).
- **File Upload**: 50MB limit, allowed extensions in `Config.ALLOWED_EXTENSIONS`
- **Input Sanitization**: `Validators.sanitize_filename()` cleans attachment filenames

### Database Schema

**emails table**:
- Stores email metadata and processing status
- `email_id` (UNIQUE): IMAP message ID
- `is_invoice`, `processed`: Boolean flags for workflow

**invoices table**:
- Stores OCR-extracted invoice data
- Foreign key: `email_id` references `emails.email_id`
- Fields: invoice codes/numbers, buyer/seller info, amounts, tax
- `ocr_confidence`: Float tracking recognition quality

**config table**:
- Key-value store with encryption support
- `encrypted` boolean flag determines if `CryptoUtil` decryption needed
- Used for QQ Mail credentials and app settings

### Frontend Architecture

- **Templates**: Jinja2 templates in `app/templates/`
  - `base.html`: Base layout — navbar, `.app-container`, all asset tags
  - Page templates: `index.html`, `upload.html`, `config.html`, `email_list.html`, `invoice_list.html`
- **Static Assets**: `app/static/js/` contains jQuery-based interactivity
  - `main.js`: shared helpers — `DT_LANG_ZH` (inline DataTables 中文包), `initDataTable()`,
    CSRF header wiring, SweetAlert2 wrappers
  - `invoice.js`: Invoice-specific features
- **UI Libraries**: Bootstrap 5, DataTables, SweetAlert2, Font Awesome

**All vendor assets are local, under `app/static/vendor/`. Never switch a tag back to a CDN.**
The app is distributed as a PyInstaller bundle to non-technical users; a CDN reference means
the UI renders unstyled whenever they are offline or their network blocks jsdelivr/cdnjs.
The same rule applies to the DataTables i18n file — it is inlined as `DT_LANG_ZH` in `main.js`.
`bill_app.spec` bundles `app/static` wholesale, so new vendor files need no spec change.

### Visual Design

`app/static/css/main.css` is a theme layer over Bootstrap (design tokens as CSS custom
properties, then component overrides). Direction is deliberately restrained — Stripe
Dashboard / Linear rather than a colorful admin template:

- Neutral `#F7F8FA` page background, pure-white cards, 1px borders, **no drop shadows**
- A single accent color (`--app-accent`, indigo). Saturated color blocks are not used —
  the old four-color stat cards were replaced by `.stat-card` (white, thin border)
- Badges are always soft-background pills; `.bg-info/.bg-success/...` are restyled globally,
  so existing markup picks up the treatment without edits
- CJK fonts are named explicitly in the font stack — without them Windows falls back to 宋体
- Reusable patterns: `.page-header` / `.page-title`, `.stat-grid` / `.stat-card`,
  `.empty-state`, `.dropzone`, `.card-body.is-flush` (for tables), `.amount`, `.nowrap`

When adding UI, reuse these classes instead of Bootstrap's colored utilities
(`bg-primary`, `text-white` card headers, `btn-warning`, …).

### QQ Mail Integration Notes

- Uses authorization code (not password) from QQ Mail IMAP settings
- IMAP date filtering has bugs - `EmailService.fetch_emails()` includes client-side date filter as fallback
- Connection must be in SELECTED state for FETCH operations
- Email encoding detection tries multiple charsets: utf-8, gb2312, gbk, gb18030

### Invoice Parsing Notes

- **Direct parsing is the primary path.** Most Chinese electronic invoices are PDFs with a
  text layer; some embed the full invoice as XML. Neither needs network or credentials.
- OFD is a zip archive; page text lives in `<ofd:TextCode>` elements. Extracted in document
  order, then run through the same regexes as PDF text.
- Amount regexes accept 1–2 decimal places; `价税合计（小写）` is the most reliable amount,
  missing amounts are derived arithmetically from the other two.
- When tuning the regexes against real invoices, run `python test_pdf_parser.py` for regression.

### OCR Integration Notes (fallback only)

- Baidu OCR free tier: 500 calls/day
- Primary API: `vatInvoice()` for VAT invoices
- Fallback: `receipt()` for general invoices
- Returns structured data with field-level extraction
- Application handles missing OCR config gracefully: electronic invoices still work,
  only images/scans are skipped with a message pointing at `/config`

## Key Design Patterns

- **Application Factory Pattern**: `create_app()` for Flask initialization
- **Service Layer Pattern**: Business logic separated from routes
- **Static Method Pattern**: Models use static methods instead of instance methods (no ORM)
- **Strategy Pattern**: `InvoiceDetector` uses multiple detection strategies with confidence scoring
